# Proposal: provider adapters and account profiles (phase 3)

## Why

relay cannot move a job between agents until it can start, watch, stop and resume each agent through the interfaces its maker officially offers, and until it knows which account each agent runs under. This is phase 3 of `docs/ROADMAP.md`. Phase 4 (`relay switch`) and every later phase call the adapters built here, and the research shows that Claude Code and Codex now expose enough supported signals (session IDs, structured limit errors, reset times and hooks) to build them without screen scraping (`docs/research/provider-control-surfaces.md`, sections 6 to 8).

## What Changes

- **One adapter interface for every provider.** An adapter detects the installed tool and its version, starts a worker in interactive mode (in the person's own terminal) or headless mode (no person typing), sends messages, turns the tool's output into relay's own worker events, interrupts a turn, stops a worker cleanly (the `stop` operation that `relay switch` in phase 4 uses), resumes a provider session by its ID, delivers relay's instructions and the first prompt through the best channel the tool has, reports availability with the source of every reading, and installs hooks that call `relay hook`. Each adapter declares what it cannot do instead of pretending. Source: `docs/research/provider-control-surfaces.md` section 7.
- **Fake agents used by every test.** `fake-claude` and `fake-codex` are small programs that print exactly the formats of the real tools (Claude's stream JSON, Codex's app-server messages and `codex exec` lines) and follow a scenario file: say text, run a command, write a file, reach a usage limit with a reset time, crash, start slowly, hang, or finish. An in-process fake adapter serves tests of later phases. No test calls a real provider. Source: `docs/research/architecture.md` section 9, items 1 and 3.
- **The Codex adapter, through the Codex app server.** relay starts `codex app-server` per worker, uses `thread/start`, `turn/start`, `turn/steer`, `turn/interrupt` and `thread/resume`, reads usage windows and reset times with `account/rateLimits/read`, and recognises the `usageLimitExceeded` error. `codex exec --json` is the fallback when the app server cannot start. Codex hooks are written to the account's `hooks.json`, and relay tells the person to trust them once in Codex's `/hooks` screen, then checks their trust status. Source: `docs/research/provider-control-surfaces.md` sections 2.1, 2.2, 2.6, 2.7 and 8.
- **The Claude Code adapter, through `claude -p --output-format stream-json`.** relay chooses the session ID in advance with `--session-id`, for headless and interactive sessions alike, streams events, reads `rate_limit_event` and the `rate_limit` error, and launches interactive sessions in the person's terminal. It installs a `StopFailure` hook to learn when an interactive session stopped at a limit, and, only if the person agrees, a status-line command that records the 5-hour and 7-day usage and reset times. Source: `docs/research/provider-control-surfaces.md` sections 1.1 to 1.5 and 8.
- **Account profiles.** `relay account add <provider> <name>` creates a profile folder with mode 0700 (used as `CLAUDE_CONFIG_DIR` or `CODEX_HOME`), adds the account to `config.toml`, and runs the provider's own login command in the person's terminal. relay never reads, copies or stores credentials. When relay starts any agent, it removes every known credential environment variable unless the account was configured to receive one. New commands: `relay account add | list | status | login | remove`. Source: `docs/research/security.md` section 2.
- **A policy file per adapter.** Each adapter ships a reviewed file with links to the provider's terms, the date they were last checked, the allowed sign-in methods, the usage signals relay uses, and the rule that automatic switching between two accounts of the same provider is off. relay shows it when an account is added and with `relay policy show <provider>`. Source: `docs/research/security.md` section 7.
- **Hook setup.** `relay hooks install | remove | status <account>` adds or removes relay's hook entries, which call `relay hook <provider> <event>`, without touching the person's other hooks. `relay hook` records events in a spool file in this phase; phase 5 adds delivery to the daemon. `relay statusline claude` is the optional status-line wrapper. Source: `docs/research/architecture.md` section 6.
- **`relay run`.** The command that starts an agent inside a relay job, in interactive mode by default or with `--headless --prompt <text>`, records the worker and the facts it observes (worker started, session identified, command ran, file changed, turn completed or failed, availability, worker ended) in `.relay/events.jsonl`, and keeps the raw output in a private log. This change builds the basics of `relay run`; `add-relay-switch` adds only the handoff parts (start and continuation prompts, the allow-list question, switch requests and the checkpoint when the agent exits). Source: `VISION.md` ("The first version") and earlier research on agent session formats ("Lessons from jstack").
- **Contract tests against recorded fixtures.** One shared test suite that every adapter must pass, run against fixture files of real output. The first fixtures are built from the documented formats and marked as such; Josué records real ones once with an opt-in script. Source: `docs/research/architecture.md` section 9, item 2.

## Capabilities

### New Capabilities

- `provider-adapters`: the adapter contract: detection and versions, capabilities, interactive and headless start, standard input and output handling, normalized worker events, sending, interrupting, resuming, delivering instructions, permission levels and availability readings.
- `fake-provider`: the fake agent programs, their scenario files, and the in-process fake adapter that tests use instead of real providers.
- `adapter-contract-tests`: the shared contract suite, the fixture layout and metadata, fixture recording and redaction, and the tested-versions list.
- `codex-adapter`: driving Codex through its app server, the `codex exec` fallback, interactive launch, rate limits, the usage-limit error, sessions, and Codex hooks with their one-time trust.
- `claude-code-adapter`: driving Claude Code through `claude -p` in stream-JSON mode and interactive launch, its limit signals, the `StopFailure` hook and the status-line rate limits.
- `provider-accounts`: `relay account` commands, profile folders, sign-in through the provider's own login, the credential environment rules, and what relay may record about an account.
- `provider-policies`: the policy file of each adapter, showing and acknowledging it, staleness, and the same-provider switching rule.
- `provider-hook-setup`: installing, checking and removing relay's hooks and status line in a profile, the spool form of `relay hook`, and `relay statusline claude`.
- `agent-runs`: `relay run` in interactive and headless modes, relay's fixed instructions, worker records, the worker events written to the job's event log, and its exit codes.

### Modified Capabilities

None. No specs exist yet in `openspec/specs/`. This change depends on capabilities proposed in `add-cli-scaffold` (`relay-config`, `cli-commands`) and `add-checkpoint-engine` (`job-files`), and shares the hook allow list and spool format with `add-daemon-api-and-status` (`provider-hooks`); the points of contact are listed under Impact.

## Decisions pending Josué's decision

Approving this proposal approves each recommendation below.

1. **Automatic switching between two accounts of the same provider. Pending Josué's decision.** Recommendation: off, with no setting to turn it on in this version. Each policy file says "off", and the function that later phases ask returns false for two accounts of the same provider. Sources: `docs/ROADMAP.md` ("Decisions waiting for Josué"); `docs/research/security.md` section 7; `docs/research/provider-control-surfaces.md` section 9, decision 1.
2. **Whether relay may edit the person's agent settings to install hooks. Pending Josué's decision.** Recommendation: yes, but only after the person sees the exact entries and says yes, with a backup of the file, and never touching Codex's `notify` setting or any hook that is not relay's. `relay account add` offers it for a new profile; for an existing folder such as `~/.claude`, only `relay hooks install` does it. Without hooks, relay still sees every session it starts itself. Source: `docs/research/provider-control-surfaces.md` section 9, decision 3.
3. **Claude Code's automatic wait at the usage limit. Pending Josué's decision.** Recommendation: relay does not change the `autoContinueAtUsageLimit` setting. When an interactive Claude session waits for its reset, relay records the account as rate limited with the reset time. Source: `docs/research/provider-control-surfaces.md` section 1.4 and section 9, decision 5.
4. **Permission level of headless runs. Pending Josué's decision.** Recommendation: headless runs default to "edit in the workspace" (Claude Code `--permission-mode acceptEdits --permission-prompts none`; Codex sandbox `workspace-write` with approval policy `never`). A "read-only" level exists. "Full access" is refused in this version, and relay never passes a bypass flag. Interactive runs pass no permission flags at all, so the tool's own settings apply. Sources: `docs/research/security.md` section 5; `docs/ROADMAP.md` ("Unattended mode"); `docs/research/provider-control-surfaces.md` sections 1.6 and 2.9.
5. **Desktop apps are viewers, not something relay drives. Pending Josué's decision.** Recommendation: relay drives only the command-line programs. It observes desktop-app sessions through the same hooks, because they read the same settings, and never automates app windows. Source: `docs/research/provider-control-surfaces.md` section 9, decision 8.
6. **Runtime.** This change assumes TypeScript on Bun, as phase 1 recommends (also pending). Source: `docs/research/architecture.md` section 1.

The design also makes smaller choices that are approved with this proposal: the Claude Code adapter runs the `claude` program directly rather than through the Agent SDK (design decision 3); Codex uses the app server first and `codex exec` only as a fallback (design decision 4); relay requires the tool versions its fixtures were recorded with or newer (design decision 2).

## Out of scope

- `relay switch`, the handoff builder, the content of `checkpoint.md`, the secret scan of handoff prompts, and the confirmation before a job first goes to a new provider (phase 4). `relay run` only refuses an account that the project's allow list excludes.
- The daemon, the local API, SQLite and `relay status` (phase 5). In this phase `relay hook` writes to the spool file only, and `relay run` reads that file itself.
- Automatic failover and any action taken on a limit (phase 7). Readings are recorded and shown, nothing more.
- Cursor, OpenCode and T3 Code adapters. Their findings are noted in `design.md` for later adapters only.
- Driving desktop apps, the Claude Agent SDK, the Codex TypeScript SDK, the Codex shared daemon socket (`codex app-server proxy`), and reading any provider transcript file.
- Unattended mode, worktree creation, and any "full access" permission level.

## Security

This change starts other companies' programs, handles where their logins live, and edits their settings files.

- **Credentials.** relay never reads, copies, stores, logs or forwards a token, a credential file or a Keychain entry. Sign-in happens only through `claude auth login` or `codex login`, run in the person's terminal with the profile variable set; relay does not capture that terminal. relay stores only the authentication method reported by the provider's status command, never the email. Source: `docs/research/security.md` section 2, "The rule" and "What relay may record about an account".
- **Environment.** Every agent starts with all variables beginning with `ANTHROPIC_` or `OPENAI_` removed, plus `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `AWS_BEARER_TOKEN_BEDROCK`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `CURSOR_API_KEY`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME`. relay then adds only the account's profile variable, the credential variables the account lists in `credential_env`, and relay's own `RELAY_HOME`, `RELAY_JOB`, `RELAY_TARGET` and `RELAY_WORKER`, and never passes one provider's variables to another provider's program. Source: `docs/research/security.md` section 2, "Clean the environment".
- **Profile folders.** Folders relay creates have mode 0700. relay refuses to use one that another user owns or that group or others can write. Source: `docs/research/security.md` section 2.
- **Settings files.** Installing hooks shows the change, asks first, backs up the file, writes it atomically and touches only relay's own entries. relay never pre-accepts Codex's hook trust prompt or any folder-trust prompt. Source: `docs/research/security.md` section 5, "Prompt injection", item 4.
- **Prompt injection.** Only relay-written text goes into the system channel (`--append-system-prompt`, `developerInstructions`). Agent-written files such as `.relay/checkpoint.md` are only named in the first prompt, never copied into the system channel. Invisible characters (the one list in `src/text/invisible.ts` from `add-checkpoint-engine`) are removed from all text relay sends. Source: `docs/research/security.md` section 5, "Prompt injection", items 1 and 2.
- **Permissions.** relay adds no bypass flag, never answers a permission request for the person, and stops a headless run that asks for one. Source: `docs/research/security.md` section 5.
- **Processes.** relay signals only the child process it started and still holds, never a process found by name or port. Source: earlier research on agent session formats, "relay must interrupt only processes it owns".
- **Logs and events.** Raw agent output goes to `RELAY_HOME/logs/workers/` with mode 0600, outside the project, and is deleted after 14 days. `.relay/events.jsonl` receives facts only, with command lines passed through a redaction step and never message text or command output. Sources: `docs/research/architecture.md` section 8; `docs/research/security.md` section 3.
- **Terms.** Each adapter's policy file records the terms it relies on, and same-provider automatic switching stays off. Source: `docs/research/security.md` section 7.

## Impact

- New code under `src/adapters/` (core, `claude/`, `codex/`), `src/accounts/`, `src/policies/`, `src/hooks/`, `src/run/`, `src/core/config/edit.ts`, `src/secrets/redact.ts`, `src/platform/clock.ts` and `src/cli/commands/` (`run.ts`, `account.ts`, `hooks.ts`, `hook.ts`, `statusline.ts`, `policy.ts`, `providers.ts`); tests and fakes under `test/adapters/`, `test/fakes/` and `test/fixtures/providers/`; scripts `scripts/record-fixture.ts`, `scripts/check-policies.ts` and `scripts/check-codex-protocol.ts`.
- New commands: `relay run`, `relay account add | list | status | login | remove`, `relay hooks install | remove | status`, `relay hook` (spool form), `relay statusline claude`, `relay policy show`, `relay providers`. New exit codes 20 to 25 in the range the scaffold leaves free.
- Uses `add-cli-scaffold`: the command entries for `run`, `account` (one to three arguments, as in `relay account add <provider> <name>`), `providers`, `policy`, `hooks`, `hook` and `statusline`, which the scaffold already lists; the `Account` and `Provider` types; and the scaffold's rule that relay writes `config.toml` only for its own settings. `relay account add` and the first `relay run` in a project append accounts and `[[projects]]` allow lists through the one writer this change builds, `src/core/config/edit.ts`; relay never writes a credential there.
- Shares with `add-daemon-api-and-status`: this change builds the spool-only part of `relay hook`. Both changes use the same allow list (`session_id`, `cwd`, `hook_event_name`, `error`, `notification_type`, `reason`, `source`, `model`, `turn_id`; `error` is the field name Claude Code's hooks page documents for `StopFailure`, which `architecture.md` section 6 calls `error_type`), the same `profile` field and the same spool line format. Phase 5 then adds delivery to the daemon and moves spool reading from `relay run` into the daemon.
- Uses `add-checkpoint-engine`: `.relay/state.json` to find the job and its worktree root, `appendEvent` in `src/job/events.ts` for the new event types, the job lock module, and `removeInvisible` in `src/text/invisible.ts`.
- Used by `add-relay-switch`: the `stop` operation, interactive Claude Code sessions started with `--session-id`, `relay run`, the instructions in `src/run/instructions.ts`, and the `config.toml` writer.
- New files under `RELAY_HOME`: `profiles/<provider>-<name>/` (0700), `accounts/<provider>-<name>/` (account record, availability, settings backups), `jobs/<job>/workers/<worker>.json`, `locks/<job>.worker.lock` (`add-relay-switch` adds fields to it), `logs/workers/<job>-<worker>.log`, `spool/hooks.jsonl`.
- New documentation: `docs/accounts.md`, `docs/adapters.md`, `docs/hooks.md`, `docs/testing-adapters.md`.
- No new runtime dependency. External requirements: Claude Code 2.1.282 or newer, Codex 0.160.0 or newer, each only for the provider in use.
